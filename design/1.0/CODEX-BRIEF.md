# Brief for the implementing agent

You are implementing **Atlas 1.0**, a redesign of the Atlas plugin for DeepSeek Harness (DSH), from
a finished design. The design decisions are made; your job is to build them exactly, with tests, and
to stop at each review gate. This session covers the milestone named in your prompt (normally
**M0 and M1**); stop at its gate.

## Read first, in this order

1. `design/1.0/README.md`, then `SPEC.md`, `VISUAL.md`, `TEAM.md`, `PLAN.md` — all of them, before
   writing code. Requirement IDs (`SH-3`, `DK-8`, `TM-21` …) are how your work is reviewed.
2. `design/1.0/mockups/atlas-1.0.html` in a browser (screen and theme switcher at the top). Its CSS
   is the reference implementation of VISUAL.md: copy it rather than re-deriving values.
3. The code you will change: `client/*.js` (read `build-client.mjs` first), `lib/*.js`, `index.js`,
   `test/*.mjs`, `docs/guide.md`.

## How this codebase works

- The client is plain JavaScript modules in `client/`, concatenated in name order by
  `build-client.mjs` into `client.js` (commit the rebuilt `client.js`). **They share one scope**: a
  later top-level declaration with the same name silently replaces an earlier one; a test forbids
  duplicates. New modules use the numbering in PLAN.md.
- React comes from the host; elements are created with `h(...)` (no JSX). DSH services come through
  `svc('sessions' | 'workspaces' | 'uiWorkspace' | 'conversation')` and the `ctx.inject` calls in
  `client/90-register.js`; the embedded conversation uses the session-scoped slot recipe in
  `client/60-threads.js` (`SlotKit`, `EmbeddedConversation`). Keep using those patterns.
- Styles are one template string in `client/80-styles.js`; tokens are generated by
  `client/05-theme.js`. The server is `index.js` plus `lib/*.js`; routes are in `lib/routes.js` with
  the plugin's auth; state lives in the configured `stateDir`.
- Tests use `node:test`: `npm test` (unit and host) and `npm run test:dsh` (a throwaway headless DSH
  profile). Both must pass at every commit.
- DSH internals you may need are inside
  `%LOCALAPPDATA%\Programs\DeepSeek Harness\resources\app.asar\dsh\node_modules\@deepseek-ai\`
  (READMEs and TypeScript sources: `dsh-agent-team`, `dsh-tool-subagent`, `dsh-subagent`,
  `dsh-client-ui-layout`, `dsh-client-ui-model-selection`). Read them with
  `ELECTRON_RUN_AS_NODE=1 "<DSH exe>" -e "…fs.readFileSync…"`; never modify them.

## Hard rules

- Work only inside this repository, on the milestone branch named in PLAN.md. Commit locally per
  task. **Never** push, merge into `main`, install, or touch `F:\AI_Workspace\aitp-atlas` or anything
  under `~/.dsh`.
- No Oh-My-BBFF. No new runtime dependencies (ask in your milestone report if one seems
  unavoidable).
- Never read or copy the researcher's real research tree into code, tests, fixtures or screenshots.
  Use `test/fixture.mjs` and the preview harness (M0).
- Keep LF line endings. Before each commit run `git diff --stat`; if whole files appear changed, the
  line endings flipped — fix that before committing.
- Class names are global inside DSH's page. The mockup's short names (`.tab`, `.card`, `.row`,
  `.btn`, `.chip`, `.label` …) are for the mockup only: translate every one to
  `atlas-<component>[-<part>]` (the existing convention) when you port its CSS. Two collisions in the
  mockup itself (`.label`, `.sel`, `.pr`) had to be fixed during review; do not reintroduce any.
- Every color, type size, space, radius, shadow and duration comes from the tokens in VISUAL.md.
  No new raw values; if you need one, record it in the milestone report and use the nearest token.
- One primary action per region; icon-only buttons always get `aria-label` and a tooltip; status is
  never shown by color alone.
- When SPEC and a mockup disagree, SPEC wins. When SPEC is silent, follow the mockup. When neither
  covers a case, choose the option most consistent with VISUAL §1's six rules and record it.
- If a DSH API behaves differently from what SPEC assumes, probe it, degrade as QB-3 says, and
  record what you found. Do not invent private DSH APIs.

## Working through a milestone

1. Write the task list for the milestone from PLAN.md into
   `design/1.0/reports/M<n>.md` (heading "Plan"), in order.
2. For each task: implement, add the tests PLAN.md lists, run both test suites, rebuild
   `client.js`, check the screen in the preview (`npm run preview`) in both themes and at 1440×900
   and 1024×768, then commit `M<n>.<k> <Task name>`.
3. At the end: fill in the report — for every requirement ID in the milestone: **done**, **changed**
   (what and why) or **not done** (why); tests added; console errors seen (should be none); known
   gaps; questions for the design lead. Then stop and say so.

## The visual direction

Atlas 1.0 is a **celestial atlas** (VISUAL §1): the observatory by night, the engraved chart by day.
Three things in it are easy to get wrong:

- **The serif.** Source Serif 4 is vendored and used for the research's voice (titles, the greeting,
  reading, small-caps labels via `font-variant-caps: all-small-caps`, italic counts and times). The
  sans is for controls only. Do not substitute another font or drop the small caps.
- **The drawings are computed.** The sky band (VISUAL §6.7) and the constellation (§6.10) in the
  mockups are hand-placed illustrations of the rules. In Atlas they come from pure layout functions
  (`client/22-sky.js`, `client/67-constellation.js`) that turn the overview or the team state into
  positions, deterministically, with unit tests. Render them as SVG with tokens for every color, make
  every star a focusable button with a label, provide the text alternatives the spec names, and stop
  the twinkle and flow animations under `prefers-reduced-motion`.
- **Ornament carries data.** Do not add stars, gradients, glows or textures anywhere the spec does not
  put them; reading surfaces have none.

## Quality bar

The researcher's previous experience was that generated interfaces looked rough. This milestone is
reviewed side by side with the mockups: sizes are measured, colors are compared, states (hover,
focus, selected, disabled, empty, loading, error) are exercised. Match the mockups' spacing and type
exactly, keep surfaces flat, and leave nothing unstyled. A smaller amount of work done precisely is
better than a larger amount done approximately; if time runs short, finish fewer tasks completely
and report the rest as not done.
